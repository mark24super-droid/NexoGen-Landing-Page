MASTER BUILD PROMPT — NexoGen AI Business Landing Page Builder

1. YOUR ROLE

Act as a senior full-stack engineer, AI product architect, UI/UX designer, and visual website-builder specialist.

Build a functional, production-oriented web application named NexoGen.

NexoGen is an AI-powered visual website builder designed specifically for generating and editing professional business landing pages.

The application must combine:

1. AI-powered landing page generation.
2. A professional drag-and-drop visual editor.
3. Real-time website preview.
4. Direct visual editing of page elements.
5. Responsive mobile and desktop layouts.
6. AI-assisted editing.
7. Project saving and loading.
8. Exporting and publishing capabilities.

Do not create a generic ChatGPT clone, a static dashboard, or a non-functional design prototype.

The main product experience must focus on creating professional business landing pages without requiring users to write code.

---

2. IMPORTANT DEVELOPMENT RULES

Before writing any code:

1. Inspect the existing Replit project and identify its framework, package manager, directory structure, dependencies, routes, and existing functionality.
2. Reuse working components and configurations whenever possible.
3. Do not unnecessarily replace existing working files.
4. If the project is empty, initialize a suitable React + TypeScript application.
5. Make incremental changes and test each major feature.
6. Never claim a feature works unless it has been implemented and tested.
7. Do not use fake buttons, decorative controls, placeholder editor interactions, or simulated successful publishing.
8. Do not rewrite the entire application when a smaller change is sufficient.
9. Keep API keys and secrets exclusively on the server.
10. Ensure the application runs using Replit's actual configured development command and port.

If a requirement is too large to complete in one pass, first build a working end-to-end MVP, then implement the remaining features in prioritized phases.

4. DESIGN SYSTEM

Create a polished, modern, minimal, professional interface.

Use this visual direction:

- Application background: #0B0B0F
- Panel background: #13131A
- Elevated surfaces: #1A1A22
- Primary accent: #4F6BFF
- Primary text: #F5F5F7
- Secondary text: #A1A1AA
- Borders: subtle dark neutral borders
- Border radius: 8–12px
- Typography: Inter or a similar modern sans-serif
- Use consistent spacing and typography scales.
- Avoid excessive gradients, neon colors, glassmorphism, and unnecessary animations.

The generated customer websites must have their own independent design system. Do not force every generated website to use NexoGen's dark theme.

The generated landing pages should adapt their colors, fonts, layouts, and imagery to the customer's business and chosen style.

Build a responsive interface that works on Android phones, tablets, and desktop browsers.

8. DRAG-AND-DROP ENGINE

Use a maintained React-compatible drag-and-drop solution, such as dnd-kit, or a suitable visual-editor framework.

Evaluate Puck as a possible foundation for the structured visual editor before building a complete custom editor from scratch.

The drag-and-drop system must support:

1. Dragging sections from the sidebar into the canvas.
2. Reordering existing sections.
3. Adding elements to valid containers.
4. Reordering elements within containers.
5. Moving elements between compatible containers.
6. Visual drop indicators.
7. Clear drag handles where appropriate.
8. Touch-friendly interactions on mobile.
9. Correct selection and focus behavior.
10. Undo and redo integration.

Use stable IDs for every element and section.

Never identify elements solely by their array position.

Prevent invalid nesting, duplicate IDs, accidental deletion, and corrupted layouts.

If using Puck or another editor framework, customize its UI to match NexoGen's design system.

Do not build a fake drag-and-drop experience using buttons that merely simulate movement.

9. STRUCTURED PAGE DATA MODEL

Represent each landing page as structured, validated data.

Use a schema such as Zod to validate AI-generated page data before rendering.

A page should contain:

- Project metadata
- Business information
- Global design tokens
- Page settings
- Responsive configuration
- An ordered list of sections
- Nested elements
- Stable element IDs
- Section-specific properties

A simplified conceptual example:

{
"version": 1,
"project": {
"name": "Example Gym",
"businessType": "gym"
},
"theme": {
"primaryColor": "#4F6BFF",
"fontFamily": "Inter"
},
"sections": [
{
"id": "hero-unique-id",
"type": "hero",
"props": {
"heading": "Build Your Strongest Self",
"description": "Training designed around your goals.",
"buttonLabel": "Join Today"
},
"children": []
}
]
}

This example is illustrative, not a complete schema.

Implement the real schema with strict validation, defaults, versioning, and safe error handling.

Use a renderer that maps approved component types to React components.

Do not directly execute arbitrary AI-generated JavaScript inside the editor.

11. AI PROVIDER INTEGRATION

Use a configurable AI provider.

Groq may be used if a compatible model is available for the required structured output.

Requirements:

- Read API credentials from server-side environment variables.
- Never expose secrets to frontend code.
- Add request timeouts and error handling.
- Validate all model output.
- Limit prompt and response sizes.
- Add reasonable generation limits.
- Handle rate limits.
- Show useful error messages.
- Keep provider integration isolated from UI components.
- Support changing the model without rewriting the application.

If the API key is unavailable, provide a clearly labelled demo mode using local example templates.

Demo mode must not pretend that real AI generation occurred.

Do not hardcode API keys.

12. AI-ASSISTED VISUAL EDITING

Add an AI assistant panel inside the workspace.

Users should be able to select a section and issue instructions such as:

- "Make this hero section more premium."
- "Rewrite this text for Indian customers."
- "Change the CTA to WhatsApp enquiry."
- "Make these pricing cards easier to compare."
- "Improve the mobile layout."
- "Add a testimonial section below the features."
- "Change the visual style to minimal and elegant."

When a section is selected:

1. Send the selected component data and relevant page context to the backend.
2. Generate a proposed structured update.
3. Validate the update.
4. Show a preview or proposed change.
5. Apply the update only when valid.
6. Record the change in undo history.

Do not allow the AI to silently replace unrelated page sections.

Support page-level instructions only when the user explicitly requests broader changes.

Preserve manually edited content unless the requested change requires modifying it.

14. UNDO, REDO, AUTOSAVE, AND PROJECT MANAGEMENT

Implement:

Undo and redo

- Store meaningful editor state changes.
- Support multiple undo and redo operations.
- Group rapid typing into sensible history entries.
- Prevent history from growing without limits.

Autosave

- Debounce frequent edits.
- Display saving, saved, and failed-to-save states.
- Prevent stale requests from overwriting newer changes.
- Recover unsaved edits when practical.

Project management

- Create a new project.
- Open a saved project.
- Rename a project.
- Duplicate a project.
- Delete a project with confirmation.
- Display recently edited projects.

Persist projects in a database when configured.

If persistent storage is unavailable, implement a clearly documented local demo mode without claiming that projects are stored in a cloud database.

Support:

- Uploading images.
- Selecting a replacement image.

- Editing alt text.

16. EXPORTING AND PUBLISHING

Implement a reliable publishing workflow.

Export

Provide:

- Downloadable HTML/CSS where supported.
- Project data export as JSON.
- A documented export structure.
- A clear indication of any limitations.

Exported HTML should include semantic markup, responsive styling, and the required assets or valid asset references.

Do not claim that a page is fully portable if it depends on an unavailable backend.

Publishing

Provide a Publish button.

A successful publishing workflow must:

1. Validate the page.
2. Generate the publishable output.
3. Upload or deploy it using a configured hosting provider.
4. Verify that deployment succeeded.
5. Return the actual published URL.
6. Show a clear success or error state.

Do not show a fake live URL or report success before the hosting provider confirms deployment.

If hosting is not configured, show a working preview and a clear publishing setup message.

Design the publishing architecture so a hosting provider can be added later.

17. SECURITY

Treat all user content and AI-generated data as untrusted.

Implement:

- Server-side API key protection.
- Input validation.
- Output schema validation.
- Safe URL handling.
- Protection against script injection.
- Sanitization of user-generated HTML where applicable.
- Authentication and project ownership checks when accounts are enabled.
- Server-side authorization for saving, editing, exporting, and publishing.
- Request size limits.
- Rate limiting where practical.
- Safe error messages that do not expose secrets.
- Secure handling of file uploads.

Do not use eval or execute arbitrary model-generated scripts.

Do not allow one user to access another user's private projects.

Never expose service-role credentials or privileged database keys to the browser.
